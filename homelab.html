Homelab

A hypervisor, a firewall and one managed switch, set up so a deliberately vulnerable machine can sit next to my documentation without trusting it. The interesting part is not the hardware — it is the segmentation, the consumer gear, and the fact that none of it counts until it is written down.

01Why a lab at all

You cannot learn segmentation from a book. You can read that VLANs isolate broadcast domains and that a firewall filters between them, and still spend a weekend on a rule that silently drops DNS because it sits above the allow. The lab exists so those mistakes cost an evening instead of a client.

The second reason is less flattering: I wanted somewhere to run deliberately vulnerable software. A target machine that exists to be broken has to be isolated from everything that matters — which turns "set up a VM" into a real network design problem.

02The shape of it

Three layers. The home router provides the uplink and nothing else. Behind it, a virtualised firewall owns the lab network: it is the only thing that routes between the lab and the house. The hypervisor sits on both sides — one interface facing management, one facing the lab — and the managed switch carries the tagging.

03The constraint that taught me the most

The switch is a consumer managed switch — a real one, with a real web UI, but not enterprise. It does not do per-port hybrid tagging the way a data-centre switch does: you assign a PVID to a port and the port carries one untagged VLAN. Fine for access ports; restrictive when one physical host needs to be on two networks.

The way out was to stop fighting it: two physical interfaces on the hypervisor, one per segment, and a switch port plan where every port is an access port. No trunk, no native-VLAN subtleties, nothing to misconfigure at 1 a.m. The limitation produced a simpler design than the "proper" one would have.

Lesson

When the hardware will not do the elegant thing, the honest move is to change the design — not to write a config you cannot explain to yourself three months later.

04Documentation is the deliverable

Every non-obvious decision gets a numbered entry with the reasoning and the alternative that was rejected. Four exist so far: the overall design direction, running containers rootless rather than as root, the logo geometry, and the decision to keep a separate engineering vault instead of scattering notes across projects.

The test I apply: if I come back in six months, can I tell why the firewall rule is there — not just that it exists? A config without the reason attached is a config nobody will dare change.

05What is published, and what is not

The architecture documentation is public, because the reasoning is worth sharing and the writing is part of the work. The addresses are not.

  • Public: design reasoning, VLAN plan at the concept level, configuration approach, troubleshooting history, lessons learned.
  • Private: exact IPs, the per-port VLAN map, the master PDF compilation, and the engineering vault with runbooks and build logs.
  • Why: a network map is reconnaissance material. Publishing which subnet the firewall lives on, which ports are access ports and where the hypervisor's management interface sits saves an attacker the first hour of an engagement — for no benefit to a reader who wants to learn.

The public repository was audited and redacted after the fact: addresses were replaced with placeholders, and the compiled PDF was removed because it contained the full detail and could not be redacted in place.

06What's next

  • ZFS storage pool — planned, not built, and documented as such.
  • An inventory and health-check tool so "what runs where" stops living in a markdown table.
  • Backups with a restore that has actually been tested, not just configured.
